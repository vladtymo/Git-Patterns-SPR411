The Visitor Pattern

Separate algorithms from the objects they operate on. Visitor lets you add new operations to a stable object structure without changing its classes.

Problem

Imagine a stable collection of objects. You need to add several unrelated operations, such as exporting, validating, and calculating prices. Adding every operation to every element class makes those classes large and tightly coupled.

When to Use

  • You have a stable hierarchy of elements.
  • You need several unrelated operations over those elements.
  • You want to keep algorithms out of the element classes.
  • You expect to add operations more often than element types.
Warning: Adding a new element type requires updating every visitor implementation.

Checklist

  • Visitor interface
  • Concrete visitors for operations
  • Element interface with accept()
  • Double dispatch between elements and visitors
  • Stable element hierarchy

Idiomatic Implementations

TypeScript — double dispatch

interface Visitor {
  visitFile(file: File): void;
  visitFolder(folder: Folder): void;
}

interface Element {
  accept(visitor: Visitor): void;
}

class File implements Element {
  accept(visitor: Visitor) {
    visitor.visitFile(this);
  }
}

Java — operation in a concrete visitor

interface Visitor {
  void visit(Circle circle);
  void visit(Rectangle rectangle);
}

class AreaVisitor implements Visitor {
  public void visit(Circle circle) { /* calculate area */ }
  public void visit(Rectangle rectangle) { /* calculate area */ }
}

Python — explicit visitor protocol

class ExportVisitor:
    def visit_file(self, file):
        return file.name

class File:
    def accept(self, visitor):
        return visitor.visit_file(self)

Pros & Cons

Benefits

  • Groups related operations in one visitor.
  • Adds operations without editing elements.
  • Can accumulate state while traversing.

Pitfalls

  • Every visitor changes when an element is added.
  • Visitors may need implementation details.

Alternatives

  • Polymorphism: put behavior directly on each element.
  • Strategy: swap one algorithm behind an interface.
  • Pattern matching: use exhaustive type handling.

Testing Tips

  • Test each accept() dispatch independently.
  • Verify every visitor handles every element.
  • Keep visitor output deterministic.

Common Gotchas & Hardening

  • Element churn: frequent new element types increase maintenance.
  • Encapsulation: expose only the data visitors need.
  • Traversal: keep tree traversal separate when possible.
