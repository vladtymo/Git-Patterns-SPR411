The Prototype Pattern

Create new objects by cloning configured prototypes instead of rebuilding them from scratch. This keeps your code flexible, fast, and independent from concrete classes.

Problem

Say you have an object, and you want to create an exact copy of it. How would you do it? First, you have to create a new object of the same class. Then you have to go through all the fields of the original object and copy their values over to the new object. Nice! But there’s a catch. Not all objects can be copied that way because some of the object’s fields may be private and not visible from outside of the object itself.


Solution

The Prototype pattern delegates the cloning process to the actual objects that are being cloned. The pattern declares a common interface for all objects that support cloning. This interface lets you clone an object without coupling your code to the class of that object. Usually, such an interface contains just a single clone method. The implementation of the clone method is very similar in all classes. The method creates an object of the current class and carries over all of the field values of the old object into the new one. You can even copy private fields because most programming languages let objects access private fields of other objects that belong to the same class. An object that supports cloning is called a prototype. When your objects have dozens of fields and hundreds of possible configurations, cloning them might serve as an alternative to subclassing.

When to Use

  • You need many similar objects with a large configuration set.
  • Creation logic is expensive, but cloning a ready-made object is cheaper.
  • Your code depends on interfaces, not concrete classes.
  • You want to avoid a huge subclass tree for tiny configuration differences.
Warning: Prototype is great for object duplication, but shallow cloning can accidentally share nested references. Be careful with mutable child objects and cycles.

Checklist

  • Common clone interface or base class
  • Prototype object(s) with preconfigured state
  • Separate clone logic from construction
  • Correct handling of nested references
  • Registry for frequently reused templates

Idiomatic Implementations

JavaScript — shallow clone via prototype inheritance

class Shape {
  constructor(color, size) {
    this.color = color;
    this.size = size;
  }

  clone() {
    return Object.assign(
      Object.create(Object.getPrototypeOf(this)),
      this
    );
  }
}

const redCircle = new Shape("red", 12);
const clone = redCircle.clone();
clone.color = "blue";

TypeScript — typed clone contract

interface Prototype<T> {
  clone(): T;
}

class Circle implements Prototype<Circle> {
  constructor(
    public radius: number,
    public color: string,
    public x: number,
    public y: number
  ) {}

  clone(): Circle {
    return new Circle(this.radius, this.color, this.x, this.y);
  }
}

const original = new Circle(10, "green", 0, 0);
const copy = original.clone();

Python — copy.copy() or custom clone

import copy

class Shape:
    def __init__(self, color, size):
        self.color = color
        self.size = size

    def clone(self):
        return copy.copy(self)

base = Shape("purple", 20)
clone = base.clone()
clone.color = "orange"

Java — clone() with protected override

public abstract class Shape implements Cloneable {
  protected String color;

  public Shape clone() {
    try {
      return (Shape) super.clone();
    } catch (CloneNotSupportedException e) {
      throw new AssertionError(e);
    }
  }
}

public final class Circle extends Shape {
  private int radius;
  public Circle clone() {
    return (Circle) super.clone();
  }
}

Pros & Cons

✅ Benefits

  • Clones objects without coupling to classes
  • Reuses preconfigured prototypes
  • Removes repeated constructor setup
  • Works well with object graphs and presets

⚠️ Pitfalls

  • Shallow copies can share nested state
  • Complex circular references are tricky
  • May hide the true cost of cloning

Alternatives

  • Factory Method: best when object creation is simple and explicit.
  • Builder: useful for complex object assembly step by step.
  • Dependency Injection: best when you want explicit object configuration.

Testing Tips

  • Assert clone independence for mutable fields.
  • Check whether nested structures are deep-copied or shared.
  • Use a registry to keep prototype configuration centralized.

Anti-Patterns

  • Using shallow clones for objects with shared references.
  • Overusing clone() for every object without real gains.
  • Mutating prototype instances in place.

Common Gotchas & Hardening

  • Shallow copy: duplicated top-level object, but nested arrays/maps/objects remain shared.
  • Circular references: cloning graphs with cycles requires specialized logic.
  • Serialization: some languages can clone by serialization, but it is usually slow and brittle.
  • Thread safety: prototypes should be immutable or treated as read-only templates.
