The Facade Pattern

Provide a simple, unified interface to a complex subsystem. Below are practical examples, gotchas, and modern alternatives.

When to Use

  • You have a complex subsystem with many classes or APIs.
  • Clients should not need to understand the subsystem's internal workflow.
  • You want to reduce coupling between clients and implementation details.
  • You need a simple entry point for common operations.
Warning: Avoid turning the facade into a "god object". A facade should simplify access to a subsystem, not contain all of its business logic.

Checklist

  • Identify a complex subsystem
  • Create a simple public interface
  • Delegate work to subsystem classes
  • Keep subsystem classes independent
  • Expose only common operations

Idiomatic Implementations

Java — Simple Facade over a Complex Subsystem

class CPU {
  void freeze() {
    System.out.println("CPU frozen");
  }

  void jump(long position) {
    System.out.println("CPU jumps to " + position);
  }

  void execute() {
    System.out.println("CPU executing");
  }
}

class Memory {
  void load(long position, byte[] data) {
    System.out.println("Memory loaded");
  }
}

class HardDrive {
  byte[] read(long lba, int size) {
    System.out.println("Reading from hard drive");
    return new byte[size];
  }
}

public class ComputerFacade {
  private final CPU cpu;
  private final Memory memory;
  private final HardDrive hardDrive;

  public ComputerFacade() {
    cpu = new CPU();
    memory = new Memory();
    hardDrive = new HardDrive();
  }

  public void start() {
    cpu.freeze();

    byte[] bootData = hardDrive.read(0, 1024);
    memory.load(0, bootData);

    cpu.jump(0);
    cpu.execute();
  }
}

The client only needs to call start(). The facade hides the interaction between CPU, memory, and hard drive.

ComputerFacade computer = new ComputerFacade();
computer.start();

C# — Facade for an Order Processing System

class Inventory {
  public bool CheckStock(string product) {
    return true;
  }
}

class Payment {
  public bool Charge(string card, decimal amount) {
    return true;
  }
}

class Shipping {
  public void Ship(string product, string address) {
    Console.WriteLine("Shipping " + product);
  }
}

public sealed class OrderFacade {
  private readonly Inventory inventory = new Inventory();
  private readonly Payment payment = new Payment();
  private readonly Shipping shipping = new Shipping();

  public bool PlaceOrder(
      string product,
      string card,
      decimal amount,
      string address) {

    if (!inventory.CheckStock(product))
      return false;

    if (!payment.Charge(card, amount))
      return false;

    shipping.Ship(product, address);

    return true;
  }
}

The facade coordinates several subsystem operations and exposes one simple method to the client.

var orders = new OrderFacade();

bool success = orders.PlaceOrder(
    "Laptop",
    "4111-1111-1111-1111",
    999.99m,
    "Main Street"
);

JavaScript — Facade over Multiple Services

class AuthService {
  login(username, password) {
    console.log("Authenticating user...");
    return true;
  }
}

class UserService {
  loadProfile(username) {
    console.log("Loading user profile...");
    return {
      username,
      role: "admin"
    };
  }
}

class NotificationService {
  sendWelcome(username) {
    console.log("Sending welcome notification...");
  }
}

class AppFacade {
  constructor() {
    this.auth = new AuthService();
    this.users = new UserService();
    this.notifications = new NotificationService();
  }

  login(username, password) {
    if (!this.auth.login(username, password)) {
      return null;
    }

    const profile = this.users.loadProfile(username);

    this.notifications.sendWelcome(username);

    return profile;
  }
}

Instead of interacting with several services directly, the client uses one high-level facade API.

const app = new AppFacade();

const profile = app.login("alice", "secret");

console.log(profile);

Python — Facade for a Video Conversion System

class VideoFile:
  def __init__(self, filename):
    self.filename = filename


class Codec:
  def decode(self, file):
    print("Decoding", file.filename)


class AudioMixer:
  def fix(self, file):
    print("Fixing audio")


class VideoEncoder:
  def encode(self, file):
    print("Encoding video")


class VideoConverter:
  def __init__(self):
    self.codec = Codec()
    self.mixer = AudioMixer()
    self.encoder = VideoEncoder()

  def convert(self, filename):
    video = VideoFile(filename)

    self.codec.decode(video)
    self.mixer.fix(video)
    self.encoder.encode(video)

    print("Conversion complete")

converter = VideoConverter()
converter.convert("movie.mp4")

The client only needs to know about the facade and does not need to understand the individual conversion steps.

Pros & Cons

✅ Benefits

  • Simplifies a complex API
  • Reduces coupling between clients and subsystems
  • Centralizes common workflows
  • Improves readability and usability

⚠️ Pitfalls

  • Facade can become too large
  • May hide useful subsystem functionality
  • Can become a maintenance bottleneck
  • Does not remove the underlying complexity

Alternatives

  • Adapter: changes an existing interface so incompatible classes can work together.
  • Dependency Injection: provides dependencies explicitly instead of hiding them.
  • Service Layer: encapsulates application-level workflows and operations.
  • Direct subsystem access: useful when the underlying API is already simple.

Testing Tips

  • Test the facade workflow independently.
  • Mock subsystem dependencies when necessary.
  • Keep business logic out of the facade when possible.
  • Test subsystem classes separately.

Anti-Patterns

  • Putting all application logic into the facade.
  • Creating a facade for an already-simple API.
  • Making one facade responsible for unrelated subsystems.

Common Gotchas & Hardening

  • Too much responsibility: a facade should coordinate subsystem operations rather than become the application's main business-logic container.
  • Hidden functionality: don't force every client through the facade if advanced clients genuinely need direct subsystem access.
  • Breaking changes: keep the facade's public API stable because many clients may depend on it.
  • Large facades: if the facade grows too large, split it into smaller facades based on responsibilities.
  • Not a Singleton: a facade does not need to have only one instance. Its purpose is interface simplification, not instance control.
