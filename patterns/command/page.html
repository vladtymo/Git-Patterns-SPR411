Design Pattern - Behavioral

The Command Pattern

Turn a request into a stand-alone object that contains all information about the request. This lets you pass, queue, delay, log, and undo operations without coupling senders to receivers.

Applicability

  • Parameterize objects with operations by turning a method call into a stand-alone object.
  • Queue, schedule, log, serialize, or send operations over a network.
  • Implement reversible operations such as undo and redo.
  • Share one operation between several interface elements, such as buttons, menus, and shortcuts.
Key idea: The sender triggers a command, while the command knows which receiver to call and how to pass the request details.

Checklist

  • Command interface with execute()
  • Concrete command stores request data
  • Receiver contains business logic
  • Sender holds a command reference
  • Client wires the object graph

Structure Overview

Real-World Analogy: A Restaurant Order

A paper order is a command. It contains the meal details, waits in a queue until the chef is ready, and separates the waiter who takes the request from the chef who performs the work.

The same separation helps a text editor reuse Copy, Cut, Paste, and Undo operations from toolbar buttons, context menus, and keyboard shortcuts.

Undoable Text Editor

Each command can save the editor state before changing it. Commands that change state are added to a history stack, and the latest command can restore its saved state.

Java - Command with Undo

interface Command {
    boolean execute();
    void undo();
}

class CutCommand implements Command {
    private final Editor editor;
    private String backup;

    CutCommand(Editor editor) {
        this.editor = editor;
    }

    public boolean execute() {
        backup = editor.getText();
        editor.deleteSelection();
        return true;
    }

    public void undo() {
        editor.setText(backup);
    }
}

class Button {
    private final Command command;

    Button(Command command) {
        this.command = command;
    }

    void click() {
        command.execute();
    }
}

C# - Command with Receiver

public interface ICommand
{
    bool Execute();
    void Undo();
}

public sealed class DeleteCommand : ICommand
{
    private readonly Editor _editor;
    private string _backup = "";

    public DeleteCommand(Editor editor)
    {
        _editor = editor;
    }

    public bool Execute()
    {
        _backup = _editor.Text;
        _editor.DeleteSelection();
        return true;
    }

    public void Undo()
    {
        _editor.Text = _backup;
    }
}

var command = new DeleteCommand(editor);
var button = new Button(command);
button.Click();

JavaScript - Command as an Object

class CutCommand {
    constructor(editor) {
        this.editor = editor;
        this.backup = '';
    }

    execute() {
        this.backup = this.editor.text;
        this.editor.deleteSelection();
        return true;
    }

    undo() {
        this.editor.text = this.backup;
    }
}

class Button {
    constructor(command) {
        this.command = command;
    }

    click() {
        this.command.execute();
    }
}

const command = new CutCommand(editor);
new Button(command).click();

Python - Command History

class CutCommand:
    def __init__(self, editor):
        self.editor = editor
        self.backup = ""

    def execute(self):
        self.backup = self.editor.text
        self.editor.delete_selection()
        return True

    def undo(self):
        self.editor.text = self.backup


class CommandHistory:
    def __init__(self):
        self.history = []

    def push(self, command):
        self.history.append(command)

    def pop(self):
        return self.history.pop() if self.history else None

Implementation Steps

  1. Declare a command interface with a single execution method.
  2. Extract requests into concrete commands that store arguments and a receiver reference.
  3. Identify senders and give them command fields.
  4. Make senders execute commands instead of calling receivers directly.
  5. Create receivers, commands, and senders in that order, then associate them.

Benefits

  • Single Responsibility: Decouples classes that invoke operations from classes that perform them.
  • Open/Closed Principle: New commands can be added without changing existing client code.
  • Undo and Redo: Commands can store state or implement inverse operations.
  • Deferred Execution: Operations can be queued, scheduled, logged, or serialized.
  • Macro Commands: Simple commands can be assembled into a complex operation.

Drawbacks

  • More Classes: A command class is often needed for every request.
  • Extra Layer: The code becomes more complicated between senders and receivers.
  • State Cost: Undo histories can consume memory when commands store backups.
  • Inverse Operations: Reversing some operations can be difficult or impossible.

Relations with Other Patterns

  • Chain of Responsibility: Passes a request through a chain; Command establishes a connection between a sender and receiver.
  • Mediator: Removes direct sender-receiver connections through a mediator; Command packages the request itself.
  • Memento: Works with Command to save receiver state for undo operations.
  • Strategy: Both parameterize an object with an action, but Command represents an operation that can be queued or logged, while Strategy swaps algorithms.
  • Prototype: Can help save copies of commands in command history.
