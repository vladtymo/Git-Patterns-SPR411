The Builder Pattern

Construct complex objects step by step. Produce different types and representations of an object using the same construction code.

Intent

Builder is a creational design pattern that lets you construct complex objects step by step. The pattern allows you to produce different types and representations of an object using the same construction code.

Problem

Imagine a complex object that requires laborious, step-by-step initialization of many fields and nested objects. Such initialization code is usually buried inside a monstrous constructor with lots of parameters. Or even worse: scattered all over the client code.

For example, let’s think about how to create a House object. To build a simple house, you need to construct four walls and a floor, install a door, fit a pair of windows, and build a roof. But what if you want a bigger, brighter house, with a backyard and other goodies (like a heating system, plumbing, and electrical wiring)?

The simplest solution is to extend the base House class and create a set of subclasses to cover all combinations of the parameters. But eventually you’ll end up with a considerable number of subclasses. Any new parameter, such as the porch style, will require growing this hierarchy even more.

There’s another approach that doesn’t involve breeding subclasses: creating a giant constructor right in the base House class with all possible parameters that control the house object.

In most cases, most of the parameters will be unused, making the constructor calls pretty ugly. For instance, only a fraction of houses have swimming pools, so the parameters related to swimming pools will be useless nine times out of ten.

Solution

The Builder pattern suggests that you extract the object construction code out of its own class and move it to separate objects called builders.

The pattern organizes object construction into a set of steps (buildWalls, buildDoor, etc.). To create an object, you execute a series of these steps on a builder object. The important part is that you don’t need to call all of the steps. You can call only those steps that are necessary for producing a particular configuration of an object.

Different Builders for Different Representations

Some of the construction steps might require different implementations when you need to build various representations of the product. For example, walls of a cabin may be built of wood, but castle walls must be built with stone.

You can create several different builder classes that implement the same set of building steps, but in a different manner. Then you can use these builders in the construction process to produce different kinds of objects.

Director

You can go further and extract a series of calls to the builder steps you use to construct a product into a separate class called Director. The director class defines the order in which to execute the building steps, while the builder provides the implementation for those steps.

Note: Having a director class in your program isn’t strictly mandatory. You can always call building steps in a specific order directly from client code. However, the director class encapsulates construction routines so you can reuse them across your entire program.

Structure

  1. Builder Interface: Declares product construction steps that are common to all types of builders.
  2. Concrete Builders: Provide different implementations of the construction steps. Concrete builders may produce products that don't follow the common interface.
  3. Products: The resulting objects. Products constructed by different builders don't have to belong to the same class hierarchy or interface.
  4. Director: Defines the order in which to call construction steps, so you can create and reuse specific configurations of products.
  5. Client: Associates one of the builder objects with the director. The client initiates the build and retrieves the final product from the builder.

Pseudocode & Real-World Example

This example of the Builder pattern illustrates how you can reuse the same object construction code when building different types of products, such as cars, and create the corresponding manuals for them.

// Using Builder makes sense when products are complex and require extensive configuration.
class Car is
    // A car can have GPS, trip computer, seats, engine type, etc.

class Manual is
    // Describes every feature corresponding to the car's configuration.

// The builder interface specifies methods for creating different parts of the product.
interface Builder is
    method reset()
    method setSeats(number: int)
    method setEngine(engine: Engine)
    method setTripComputer(enabled: boolean)
    method setGPS(enabled: boolean)

// Concrete Builder: CarBuilder
class CarBuilder implements Builder is
    private field car: Car

    constructor CarBuilder() is
        this.reset()

    method reset() is
        this.car = new Car()

    method setSeats(number: int) is
        this.car.seats = number

    method setEngine(engine: Engine) is
        this.car.engine = engine

    method setTripComputer(enabled: boolean) is
        this.car.tripComputer = enabled

    method setGPS(enabled: boolean) is
        this.car.gps = enabled

    method getProduct(): Car is
        product = this.car
        this.reset()
        return product

// Concrete Builder: CarManualBuilder
class CarManualBuilder implements Builder is
    private field manual: Manual

    constructor CarManualBuilder() is
        this.reset()

    method reset() is
        this.manual = new Manual()

    method setSeats(number: int) is
        this.manual.addInfo("Seats: " + number)

    method setEngine(engine: Engine) is
        this.manual.addInfo("Engine specs: " + engine.specs)

    method setTripComputer(enabled: boolean) is
        this.manual.addInfo("Trip computer instructions")

    method setGPS(enabled: boolean) is
        this.manual.addInfo("GPS navigation manual")

    method getProduct(): Manual is
        product = this.manual
        this.reset()
        return product

// The Director defines the order of building steps
class Director is
    method constructSportsCar(builder: Builder) is
        builder.reset()
        builder.setSeats(2)
        builder.setEngine(new SportEngine())
        builder.setTripComputer(true)
        builder.setGPS(true)

    method constructSUV(builder: Builder) is
        builder.reset()
        builder.setSeats(7)
        builder.setEngine(new V8Engine())
        builder.setTripComputer(true)
        builder.setGPS(true)

// Client Code
class Application is
    method makeCar() is
        director = new Director()

        CarBuilder builder = new CarBuilder()
        director.constructSportsCar(builder)
        Car car = builder.getProduct()

        CarManualBuilder manualBuilder = new CarManualBuilder()
        director.constructSportsCar(manualBuilder)
        Manual manual = manualBuilder.getProduct()

Idiomatic Implementations

Java — Fluent Builder with Director

public class Pizza {
    private final String crust;
    private final String sauce;
    private final String cheese;
    private final List<String> toppings;

    private Pizza(Builder builder) {
        this.crust = builder.crust;
        this.sauce = builder.sauce;
        this.cheese = builder.cheese;
        this.toppings = builder.toppings;
    }

    public static class Builder {
        private String crust = "Thin";
        private String sauce = "Tomato";
        private String cheese = "Mozzarella";
        private List<String> toppings = new ArrayList<>();

        public Builder crust(String crust) { this.crust = crust; return this; }
        public Builder sauce(String sauce) { this.sauce = sauce; return this; }
        public Builder cheese(String cheese) { this.cheese = cheese; return this; }
        public Builder addTopping(String topping) { this.toppings.add(topping); return this; }

        public Pizza build() {
            return new Pizza(this);
        }
    }
}

// Usage:
Pizza myPizza = new Pizza.Builder()
    .crust("Cheesy Crust")
    .addTopping("Mushrooms")
    .addTopping("Olives")
    .build();

C# — Fluent Interface with Method Chaining

public class Computer
{
    public string CPU { get; set; } = string.Empty;
    public string GPU { get; set; } = string.Empty;
    public int RAM { get; set; }
    public int Storage { get; set; }
}

public interface IComputerBuilder
{
    IComputerBuilder SetCPU(string cpu);
    IComputerBuilder SetGPU(string gpu);
    IComputerBuilder SetRAM(int ramGb);
    IComputerBuilder SetStorage(int storageGb);
    Computer Build();
}

public class GamingComputerBuilder : IComputerBuilder
{
    private Computer _computer = new();

    public IComputerBuilder SetCPU(string cpu) { _computer.CPU = cpu; return this; }
    public IComputerBuilder SetGPU(string gpu) { _computer.GPU = gpu; return this; }
    public IComputerBuilder SetRAM(int ramGb) { _computer.RAM = ramGb; return this; }
    public IComputerBuilder SetStorage(int storageGb) { _computer.Storage = storageGb; return this; }

    public Computer Build()
    {
        var result = _computer;
        _computer = new();
        return result;
    }
}

JavaScript / TypeScript — Fluent Builder Class

class RequestBuilder {
    constructor() {
        this.url = "";
        this.method = "GET";
        this.headers = {};
        this.body = null;
    }

    setUrl(url) {
        this.url = url;
        return this;
    }

    setMethod(method) {
        this.method = method.toUpperCase();
        return this;
    }

    setHeader(key, value) {
        this.headers[key] = value;
        return this;
    }

    setPayload(data) {
        this.body = JSON.stringify(data);
        this.headers["Content-Type"] = "application/json";
        return this;
    }

    build() {
        if (!this.url) throw new Error("URL is required to build a request");
        return {
            url: this.url,
            method: this.method,
            headers: this.headers,
            body: this.body
        };
    }
}

// Usage
const req = new RequestBuilder()
    .setUrl("/api/v1/orders")
    .setMethod("POST")
    .setPayload({ item: "Keyboard", qty: 1 })
    .build();

Python — Pythonic Builder

class QueryBuilder:
    def __init__(self, table: str):
        self._table = table
        self._fields = ["*"]
        self._where_conditions = []
        self._limit_val = None

    def select(self, *fields: str) -> "QueryBuilder":
        self._fields = list(fields)
        return self

    def where(self, condition: str) -> "QueryBuilder":
        self._where_conditions.append(condition)
        return self

    def limit(self, count: int) -> "QueryBuilder":
        self._limit_val = count
        return self

    def build(self) -> str:
        query = f"SELECT {', '.join(self._fields)} FROM {self._table}"
        if self._where_conditions:
            query += f" WHERE {' AND '.join(self._where_conditions)}"
        if self._limit_val:
            query += f" LIMIT {self._limit_val}"
        return query + ";"

# Usage:
sql = (QueryBuilder("users")
       .select("id", "name", "email")
       .where("active = 1")
       .where("age >= 18")
       .limit(25)
       .build())

Pros & Cons

✅ Advantages

  • Construct objects step-by-step, defer steps, or run them recursively.
  • Reuse construction code when building varied representations.
  • Single Responsibility: Isolate complex construction logic from business code.
  • Prevents telescoping constructors with dozen unused arguments.

⚠️ Disadvantages

  • Overall code complexity increases because you must create multiple new classes.
  • High ceremony for simple objects with few fixed fields.

Applicability

  • Eliminate telescoping constructors: When you have constructors with 10+ optional parameters.
  • Multiple representations: When code needs to assemble different representations of the same core product (e.g. wooden vs. stone house).
  • Building Composite trees: When you need recursive step-by-step construction of hierarchical object graphs.

How to Implement

  • 1. Clearly define common construction steps.
  • 2. Declare these steps in the base Builder interface.
  • 3. Implement concrete builder classes and a product retrieval method.
  • 4. (Optional) Create a Director class for predefined build routines.
  • 5. The client associates builder with director and retrieves the product.

Relations with Other Patterns

  • Factory Method vs. Builder: Many designs start by using Factory Method (less complicated and more customizable via subclasses) and evolve toward Abstract Factory, Prototype, or Builder (more flexible, but more complicated).
  • Builder vs. Abstract Factory: Builder focuses on constructing complex objects step by step. Abstract Factory specializes in creating families of related objects immediately.
  • Builder & Composite: You can use Builder when creating complex Composite trees because you can program its construction steps to execute recursively.
  • Builder & Bridge: You can combine Builder with Bridge: the director class plays the role of the abstraction, while different builders act as implementations.
  • Singletons: Abstract Factories, Builders and Prototypes can all be implemented as Singletons.
