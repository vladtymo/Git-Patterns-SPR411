The Proxy pattern

Control access to objects through a substitute that can add checks, lazy loading, caching, or logging without changing the original object.

Real document example

Think of a document service as the real subject. A document proxy controls access to that service, checking permissions before forwarding requests to the real object.

This is exactly how the Proxy pattern works: it provides the same interface as the real subject while controlling when and how the underlying object is accessed.

When to Use

  • You need to add responsibilities to an object dynamically at runtime.
  • You want to extend behavior without changing the original class or creating a large inheritance tree.
  • You need transparent composition such as logging, caching, validation, or metrics.
Rule of thumb: Use the Proxy pattern when access to an object needs control, protection, delayed creation, or additional monitoring.

Checklist

  • Shared Component interface or base class
  • Concrete implementation with core behavior
  • Proxy with the same interface as the real subject
  • Access checks or behavior around delegated calls
  • Delegation, not inheritance, as the access mechanism

Idiomatic Implementations

Java — Subject interface + proxy

interface DocumentService {
    String fetch(String path);
}

class RealDocumentService implements DocumentService {
    public String fetch(String path) { return "Contents of " + path; }
}

class DocumentProxy implements DocumentService {
    private DocumentService service;
    private boolean authorized;
    DocumentProxy(DocumentService service, boolean authorized) {
        this.service = service;
        this.authorized = authorized;
    }

    public String fetch(String path) {
        if (!authorized) throw new SecurityException("Access denied");
        return service.fetch(path);
    }
}

C# — Virtual methods with composition

public interface IDocumentService {
    string Fetch(string path);
}

public class RealDocumentService : IDocumentService {
    public string Fetch(string path) => File.ReadAllText(path);
}

public class DocumentProxy : IDocumentService {
    private readonly IDocumentService service;
    public DocumentProxy(IDocumentService service) => this.service = service;
    public string Fetch(string path) {
        if (!UserCanRead(path)) throw new UnauthorizedAccessException();
        return service.Fetch(path);
    }
}

JavaScript — Wrap an object and delegate calls

class RealDocumentService {
    fetch(path) { return `Contents of ${path}`; }
}

class DocumentProxy {
    constructor(service, canRead) {
        this.service = service;
        this.canRead = canRead;
    }
    fetch(path) {
        if (!this.canRead) throw new Error("Access denied");
        return this.service.fetch(path);
    }
}

const documents = new DocumentProxy(new RealDocumentService(), true);
console.log(documents.fetch("report.txt"));

Python — Functional-style wrappers

class RealDocumentService:
    def fetch(self, path):
        with open(path) as document:
            return document.read()

class DocumentProxy:
    def __init__(self, service, can_read):
        self._service = service
        self._can_read = can_read
    def fetch(self, path):
        if not self._can_read:
            raise PermissionError("Access denied")
        return self._service.fetch(path)

documents = DocumentProxy(RealDocumentService(), True)
print(documents.fetch("report.txt"))

Testing Tips

  • Assert the final behavior of the wrapped object, not the wrapper internals.
  • Keep proxies focused on access control or delegation.
  • Test both proxy behavior and calls forwarded to the real subject.

Anti‑Patterns

  • Proxying a class without a common interface.
  • Mutating shared state inside multiple wrappers.
  • Using proxies to hide unrelated business logic.

Common Gotchas & Hardening

  • Keep the protocol consistent: every proxy must expose the same interface as the real subject it represents.
  • Access matters: authorization and validation should happen before delegation.
  • Beware of side effects: proxies can add expensive logging or validation work.
  • Prefer delegation over deep inheritance: this keeps access responsibilities isolated and easier to test.

When and Why to Use a Proxy

Use a proxy when an object needs controlled access without changing the real subject behind it. The proxy keeps the same interface, so clients can work with it as if they were calling the original object.

Protect access

Check permissions, validate requests, or restrict sensitive operations before delegation.

Delay expensive work

Create or load the real object only when a client actually needs it.

Observe and optimize

Add logging, caching, metrics, or remote-call handling in one controlled boundary.
