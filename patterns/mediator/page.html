Design Pattern • Behavioral

The Mediator Pattern

Encapsulate communication between objects inside a mediator, reducing direct dependencies between components and keeping collaboration logic in one place.

Concept

What is the Mediator Pattern?

The Mediator is a behavioral design pattern that defines an object responsible for coordinating communication between a group of other objects.

Instead of allowing objects to communicate directly with each other, they communicate through a central Mediator.

Core idea: Objects should not know how other objects work. They only know about the mediator and communicate through it.

Structure

  • Mediator — defines communication
  • ConcreteMediator — coordinates objects
  • Colleagues — communicate through mediator
  • Client — creates and uses components
The Problem

Without a Mediator

Imagine a UI containing several components: a button, textbox, checkbox and list.

If every component communicates directly with every other component, the number of dependencies grows quickly.

How It Works

  1. A component receives an event or request.
  2. The component sends the information to the mediator.
  3. The mediator decides which components should react.
  4. The mediator coordinates the operation.

When to Use

  • Many objects communicate with each other.
  • Components become tightly coupled.
  • Communication logic is scattered across classes.
  • You want to centralize coordination.
  • You need a clean request/response pipeline.
Good signal: If changing one component requires modifying many other components, a mediator may help.
Implementation

C# — Classic Mediator

Basic Mediator

public interface IMediator
{
    void Notify(object sender, string eventName);
}

public class ConcreteMediator : IMediator
{
    public ComponentA ComponentA { get; set; }
    public ComponentB ComponentB { get; set; }

    public void Notify(object sender, string eventName)
    {
        if (eventName == "A")
        {
            ComponentB.DoSomething();
        }
        if (eventName == "B")
        {
            ComponentA.DoSomething();
        }
    }
}

public class ComponentA
{
    private readonly IMediator _mediator;

    public ComponentA(IMediator mediator)
    {
        _mediator = mediator;
    }

    public void DoSomething()
    {
        Console.WriteLine("Component A works");
        _mediator.Notify(this, "A");
    }
}

public class ComponentB
{
    private readonly IMediator _mediator;

    public ComponentB(IMediator mediator)
    {
        _mediator = mediator;
    }

    public void DoSomething()
    {
        Console.WriteLine("Component B works");
        _mediator.Notify(this, "B");
    }
}

Benefits

  • Reduces coupling between components.
  • Centralizes communication logic.
  • Makes components easier to change.
  • Improves separation of responsibilities.
  • Works well with CQRS.
  • Makes request pipelines easier to extend.

Pitfalls

  • The mediator can become a "god object".
  • Too much logic may accumulate in handlers.
  • Simple communication may become unnecessarily complex.
  • Debugging indirect communication can be harder.
  • A mediator library does not automatically create good architecture.

Testing Tips

  • Test handlers independently.
  • Mock repositories and external services.
  • Keep handlers focused on one use case.
  • Test mediator behavior only where coordination actually exists.

Good Handler

Handle()
{
    validate();
    load();
    execute();
    return result;
}

Mediator vs Service

Application Service

  • Groups related application operations.
  • Often exposes multiple methods.
  • Can become large over time.

Mediator + Handlers

  • One request represents one use case.
  • Each handler has a focused responsibility.
  • Works naturally with CQRS.
