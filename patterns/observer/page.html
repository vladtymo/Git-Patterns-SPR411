Design Pattern • Behavioral

The Observer Pattern

Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Concept

What is the Observer Pattern?

The Observer is a behavioral design pattern that allows an object (the subject/publisher) to notify other objects (the observers/subscribers) about changes in its state.

Instead of having objects periodically check for updates (polling), the subject proactively pushes notifications to a list of registered observers.

Core idea: Establish a subscription mechanism to notify multiple objects about any events that happen to the object they're observing.

Structure

  • Subject — manages observers and sends notifications
  • Observer — interface for receiving updates
  • ConcreteSubject — holds the actual state
  • ConcreteObserver — performs actions upon notification
The Problem

Without the Observer

Imagine an e-commerce system where different services need to react when an order is placed: Email Service, Inventory Service, and Analytics Service.

If the Order Service calls them directly, it becomes tightly coupled to every secondary system. Every time you add a new feature (like SMS notifications), you must modify the core Order Service.

OrderService
├──► EmailService.SendReceipt()
├──► InventoryService.ReserveItems()
└──► AnalyticsService.LogSale()

Alternatively, if services continuously poll the database for new orders, it wastes CPU and network resources.

Architecture

UML Snapshot

The Subject maintains a list of Observers. When its state changes, it iterates through the list and calls the update() method on each.

How It Works

  1. Observers subscribe to the Subject.
  2. The Subject holds a list of these references.
  3. An event occurs, altering the Subject's state.
  4. The Subject iterates over its list and calls update() on each registered Observer. 
[Publisher]
 ├── Add(Subscriber A)
 ├── Add(Subscriber B)
 │
 [State Changes]
 ├── Notify() ──► Subscriber A.Update()
 └── Notify() ──► Subscriber B.Update()

When to Use

  • Changes to one object require changing others, and you don't know how many objects need to be changed dynamically.
  • You need to avoid tight coupling between core business logic and secondary systems (like UI or logging).
  • You are building an event-driven architecture or UI framework.
Good signal: You find yourself writing code where an object calls methods on many unrelated objects just to say "I'm done updating."
Implementation

C# — Observer Approaches

Classic GoF Implementation

public interface IObserver
{
    void Update(string state);
}

public class Subject
{
    private List<IObserver> _observers = new();
    private string _state;

    public void Attach(IObserver observer) => _observers.Add(observer);
    public void Detach(IObserver observer) => _observers.Remove(observer);

    public void StateChanged(string newState)
    {
        _state = newState;
        Notify();
    }

    private void Notify()
    {
        foreach (var observer in _observers)
        {
            observer.Update(_state);
        }
    }
}

Modern C# via Events / Delegates

public class OrderService
{
    // C# provides native support for the Observer pattern via events
    public event EventHandler<OrderEventArgs> OrderPlaced;

    public void PlaceOrder(Order order)
    {
        // ... save to database ...

        // Notify all subscribers
        OrderPlaced?.Invoke(this, new OrderEventArgs { OrderId = order.Id });
    }
}

// Subscriber
public class EmailService
{
    public void Subscribe(OrderService orderService)
    {
        orderService.OrderPlaced += HandleOrderPlaced;
    }

    private void HandleOrderPlaced(object sender, OrderEventArgs e)
    {
        Console.WriteLine($"Sending email for Order {e.OrderId}");
    }
}

Reactive Extensions (Rx.NET)

// IObservable<T> acts as the Subject (Publisher)
// IObserver<T> acts as the Subscriber

public class Ticker : IObservable<int>
{
    public IDisposable Subscribe(IObserver<int> observer)
    {
        // implementation details for subscription...
        return new Unsubscriber(); // Allows clean detachment
    }
}

// Usage with LINQ
var ticker = new Ticker();
var subscription = ticker
    .Where(price => price > 100)
    .Subscribe(price => Console.WriteLine($"High price alert: {price}"));

// Unsubscribe
subscription.Dispose();
Comparison

Observer vs Pub-Sub

Though often used interchangeably, there is a distinct architectural difference:

In the Observer pattern, the Subject and Observer know about each other. The Observer explicitly registers with the Subject.

In Publish-Subscribe (Pub/Sub), there is a message broker (Event Bus) in between. Publishers and Subscribers don't know each other at all.

Observer:
Publisher ──────────────► Subscriber

Pub/Sub:
Publisher ──► [Event Bus] ──► Subscriber
