The Decorator pattern

Add behavior to objects dynamically without changing their class or forcing a large inheritance hierarchy. Below are practical examples, gotchas, and modern alternatives.

Real coffee example

Think of a plain espresso as the base object. A milk decorator adds milk, a vanilla decorator adds vanilla, and a whipped cream decorator adds a top layer. Each decorator keeps the same coffee interface while changing the final price and description.

This is exactly how the Decorator pattern works: it stacks behavior around an object instead of creating a new subclass for every possible combination.

When to Use

  • You need to add responsibilities to an object dynamically at runtime.
  • You want to extend behavior without changing the original class or creating a large inheritance tree.
  • You need transparent composition such as logging, caching, validation, or metrics.
Rule of thumb: Use the Decorator pattern when the behavior should be stacked in layers, not hard-coded into a single subclass.

Checklist

  • Shared Component interface or base class
  • Concrete implementation with core behavior
  • Decorator wrapper with same interface
  • Concrete decorators that add features
  • Composition, not inheritance, as the extension mechanism

Idiomatic Implementations

Java — Base component + decorator wrapper

interface Coffee {
  double cost();
  String description();
}

class Espresso implements Coffee {
  public double cost() { return 2.00; }
  public String description() { return "Espresso"; }
}

abstract class CoffeeDecorator implements Coffee {
  protected Coffee inner;
  CoffeeDecorator(Coffee inner) { this.inner = inner; }
}

class MilkDecorator extends CoffeeDecorator {
  MilkDecorator(Coffee inner) { super(inner); }
  public double cost() { return inner.cost() + 0.50; }
  public String description() { return inner.description() + ", milk"; }
}

C# — Virtual methods with composition

public interface ICoffee {
  double Cost { get; }
  string Description { get; }
}

public class Espresso : ICoffee {
  public double Cost => 2.00;
  public string Description => "Espresso";
}

public abstract class CoffeeDecorator : ICoffee {
  protected readonly ICoffee Inner;
  protected CoffeeDecorator(ICoffee inner) => Inner = inner;
  public abstract double Cost { get; }
  public abstract string Description { get; }
}

public class MilkDecorator : CoffeeDecorator {
  public MilkDecorator(ICoffee inner) : base(inner) { }
  public override double Cost => Inner.Cost + 0.50;
  public override string Description => $"{Inner.Description}, milk";
}

JavaScript — Wrap an object and delegate calls

class Coffee {
  getDescription() { return "Espresso"; }
  cost() { return 2; }
}

class MilkDecorator {
  constructor(coffee) { this.coffee = coffee; }
  getDescription() { return `${this.coffee.getDescription()}, milk`; }
  cost() { return this.coffee.cost() + 0.5; }
}

const order = new MilkDecorator(new Coffee());
console.log(order.getDescription(), order.cost());

Python — Functional-style wrappers

class Coffee:
    def description(self):
        return "Espresso"
    def cost(self):
        return 2.0

class MilkDecorator:
    def __init__(self, coffee):
        self._coffee = coffee
    def description(self):
        return f"{self._coffee.description()}, milk"
    def cost(self):
        return self._coffee.cost() + 0.5

order = MilkDecorator(Coffee())
print(order.description(), order.cost())

Pros & Cons

✅ Benefits

  • Extends behavior without subclass explosion
  • Composable and easy to layer
  • Open for extension, closed for modification

⚠️ Pitfalls

  • Can add many small wrapper objects
  • Debugging may be harder with stacked decorators
  • Not ideal for stateful or highly coupled features

Alternatives

  • Inheritance: works for a small fixed set of behaviors, but becomes rigid.
  • Composition: often simpler when behavior is assembled from independent services.
  • Strategy Pattern: good when changing algorithms, not object responsibilities.

Testing Tips

  • Assert the final behavior of the wrapped object, not the wrapper internals.
  • Keep decorators thin and focused on one responsibility.
  • Test order of decoration so composition remains predictable.

Anti‑Patterns

  • Decorating a class without a common interface.
  • Mutating shared state inside multiple wrappers.
  • Using decorators to hide unrelated business logic.

Common Gotchas & Hardening

  • Keep the protocol consistent: every decorator must expose the same interface as the component it wraps.
  • Order matters: adding milk before vanilla can change the description and total.
  • Beware of side effects: decorators can stack expensive logging or validation layers.
  • Prefer composition over deep inheritance: this keeps responsibilities isolated and easier to test.
